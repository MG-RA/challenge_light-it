## New authorization boundary cases

Read-only. None of them logs in or uses another account's credentials.

| Case | Result |
|---|---|
| `GET /appointments/{id}` for an appointment owned by another patient, found in the DB | **Pass**: 403, and no `patient_id` in the body. The historical cross-user 403 is now current evidence. |
| `GET /users/me` with the session token's `user_id` claim changed to another patient (signature kept) | **Pass**: 401 |
| `GET /users/me` with an `alg: none` header (original signature kept, so the request reaches the API) | **Pass**: 401 |
| `GET /users/me` with an `alg: none` header and an empty signature | **Expected failure F-20**: the Vercel firewall answers 403 first, so the API never sees the request |

A diagnostic probe during development showed that any empty-signature token, including an `HS256` header,
gets the edge 403, while the same forged header with a signature reaches the API and gets 401. Access is
denied either way. F-20 is a contract and client-handling deviation, not a disclosure.
